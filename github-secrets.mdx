部署工作流**只读 GitHub Secrets**，不读 Variables。添加位置：仓库 **Settings → Secrets and variables → Actions → Secrets** → **New repository secret**。

<Warning>
- 一定要加在 **Secrets** 标签，加到 **Variables** 不会生效
- 名称**区分大小写**（必须是 `R2_MEDIA_BUCKET`，不是 `r2_media_bucket`）
- 值只填内容，**不要**写 `NAME=...`，一般**不要**加引号
- 保存后无法再次查看原值，只能重新设置
- **改完任何 Secret 都必须重新运行一次部署工作流**——Secret 的修改不会自动同步到已部署的 Worker
</Warning>

## 必填项

这四项缺一个，部署就会直接停止。

### CLOUDFLARE_API_TOKEN

1. 登录 [Cloudflare Dashboard](https://dash.cloudflare.com)
2. 右上角头像 → **My Profile** → **API Tokens**
3. **Create Token** → **Custom token**
4. 配置权限：

| 资源 | 权限 | 为什么 |
|------|------|--------|
| Account > Workers Scripts | Edit | 部署 Worker |
| Account > D1 | Edit | 部署前执行 D1 迁移 |
| Account > Workers KV Storage | Edit | 部署 KV 绑定 |
| Zone > Cache Purge | Purge（可选） | 配合 `CF_ZONE_ID` 实现「发布即清缓存」 |

5. **Create Token** → 复制（仅显示一次）

**格式**：普通令牌字符串。

<Info>
这个 Token 有**两个用途**：一是给 GitHub Actions 里的 wrangler 部署与 D1 迁移用；二是工作流会把它**自动写成 Worker 的运行时 Secret `CF_API_TOKEN`**，供 Worker 调 Cloudflare Cache Purge 接口清边缘缓存。所以如果想让「发布即清缓存」生效，权限里要勾上 Zone > Cache Purge。
</Info>

### CLOUDFLARE_ACCOUNT_ID

1. 登录 [Cloudflare Dashboard](https://dash.cloudflare.com)
2. 选择任意域名（或看地址栏）
3. 右侧栏 → **API** → **Account ID**
4. 复制 UUID 格式的 ID

**格式**：32 位十六进制（如 `a1b2c3d4e5f678901234567890abcdef`）。

### BLOG_D1_ID

```bash
npx wrangler d1 create blog
```

输出示例：
```
✅ Successfully created DB 'blog'
database_id = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
```

复制 `database_id` 的值。

**格式**：**UUID（带横线）**，例如 `0fa366ac-f04a-4be2-8e11-5adc6ee6d686`。

<Warning>
这个值**不是数据库名**（不是 `blog`），也**不是 KV 的 id**。工作流会做格式校验：去掉横线后必须是 32 位十六进制，否则直接报错中止。
</Warning>

### BLOG_KV_ID

```bash
npx wrangler kv namespace create BLOG
```

输出示例：
```
✅ Successfully created KV namespace 'BLOG'
id = "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

复制 `id` 的值。

**格式**：**32 位十六进制**（不含横线）。工作流同样会校验格式（长度必须是 32，字符只能是 `0-9a-f`），格式不对就直接报错中止。

## 推荐项

### BLOG_ADMIN_SETUP_KEY

自行生成随机字符串：

```bash
# macOS / Linux
openssl rand -hex 32
```

```powershell
# Windows PowerShell
-join ((48..57) + (97..122) | Get-Random -Count 40 | % {[char]$_})
```

**格式**：任意足够长的随机字符串。

它的作用有**两个**：

1. **首次初始化管理员**：配置后必须携带 `X-Setup-Key` 才能设置密码（杜绝「第一个请求到的人即拿管理员」的抢注竞态）；未初始化时登录接口一律返回 403
2. **登录限流的应急通道**：登录请求带正确 `X-Setup-Key` 会**跳过全部登录限流**，但**不跳过密码校验**。所以站长永远有一条进得去的路

<Info>
未配置时退化为旧行为：首次登录自动生成随机默认密码（`xxxx-xxxx`，标记 `must_change`），存在先到先得竞态。**全新部署强烈建议配置**。
</Info>

### SITE_URL

博客对外地址，如 `https://www.2024921.xyz`（**末尾不要加 `/`**）。

**格式**：带 `https://` 的完整来源（origin），不带路径。

用途：

- 生成 RSS / Sitemap 的链接前缀
- 收紧 CORS：只允许「站点来源 + 请求自身来源」跨域读取
- 评论 / 留言板提交时的来源校验

<Warning>
**未配置 `SITE_URL` 时 CORS 是 fail-closed 的**——不返回 `Access-Control-Allow-Origin`，跨站读取会被浏览器拦下（**不是**回显任意来源）；RSS / Sitemap 则回退为用请求自身来源生成链接。所以正式站点请务必配置。
</Warning>

## 可选项

### CF_ZONE_ID

自定义域名所在 Cloudflare Zone 的 ID。控制台 → 选中你的域名 → 右侧栏 **API** → **Zone ID**。

**格式**：32 位十六进制。

配置后与 `CF_API_TOKEN`（工作流自动写入）配合，文章增删改时按 Cache-Tag 清除边缘缓存（`posts` / `feed` / `sitemap` / `post:<id>` / `stats:<id>`）。按标签清除在 Free / Pro / Business / Enterprise **都可用**（免费版 5 次/分钟、单次最多 100 个操作），详见 [Cloudflare 缓存清除文档](https://developers.cloudflare.com/cache/how-to/purge-cache/)。不配置则依赖 `s-maxage` 自然过期，功能不受影响。

### PAGES_PROJECT_NAME

<Warning>
**名字有误导性**：这个 Secret 实际的作用是**覆盖 Worker 名称**（部署命令追加 `--name <值>`），与 Pages 无关。不填则使用 `wrangler.workers.toml` 里的 `kejiland`。随意改名会部署出一个**新的 Worker**（域名 / 绑定都要重新配），新手建议不填。
</Warning>

**格式**：Worker 名称（字母 / 数字 / 连字符）。

### BLOG_WRITE_TOKEN

旧式静态写入令牌。现在的写操作走会话 token（`Authorization: Bearer <session-token>`），`BLOG_WRITE_TOKEN` 仅作为兼容保留。**新部署不需要**。

### BLOG_RATE_LIMIT_BINDING

一个**正整数**（如 `1001`），作为 Workers Rate Limiting 绑定的 `namespace_id`。

配置后会连锁触发两件事：

1. 部署工作流改用 `wrangler@^4.36.0`（该绑定要求 ≥ 4.36）
2. 向部署配置注入：

```toml
[[ratelimits]]
name = "LOGIN_LIMITER"
namespace_id = "1001"
  [ratelimits.simple]
  limit = 10
  period = 60
```

效果：登录接口在 Worker 入口按 IP 限流 10 次/分钟/位置，被拦下的请求不查库、不写库、不跑 PBKDF2。

| 情况 | 表现 |
|------|------|
| 不配置 | 行为与旧版**完全一致**：代码检测不到 `env.LOGIN_LIMITER` 就回退到 D1 计数 |
| 填了非数字 | 工作流直接报错中止（必须是正整数） |
| 账户 / 套餐不支持 | 部署会失败；删掉这个 Secret 重新部署即恢复 |

<Info>
详细的三层限流阈值与应急通道见 [安全设计](/security-overview)；三种边缘加固方案（Cloudflare Access / WAF 限流规则 / 本绑定）见 [Cloudflare Workers 部署](/cloudflare-workers)。
</Info>

## R2 存储（可选，7 个变量）

音乐与图片**共用同一组凭据**（代码只读取 `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`），所以这对凭据**必须同时有权限访问两个桶**。

| Secret | 填什么 | 格式 |
|--------|--------|------|
| `R2_ACCESS_KEY_ID` | R2 API Token 的 Access Key ID | 普通字符串 |
| `R2_SECRET_ACCESS_KEY` | R2 API Token 的 Secret Access Key（**只显示一次**） | 普通字符串 |
| `R2_ENDPOINT` | `https://<账户ID>.r2.cloudflarestorage.com` | **不带桶名、末尾不加 `/`、不是公开域名** |
| `R2_BUCKET` | **音乐桶**名，如 `qingyu-music` | 桶名 |
| `R2_PUBLIC_BASE` | 音乐桶公开域名，如 `https://music.example.com` | `https://` 开头，末尾不加 `/` |
| `R2_MEDIA_BUCKET` | **媒体桶**名，如 `qingyu-media` | 桶名 |
| `R2_MEDIA_PUBLIC_BASE` | 媒体桶公开域名，如 `https://media.example.com` | `https://` 开头，末尾不加 `/` |

<Warning>
**`R2_BUCKET` 不能为空**。工作流只有在 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、`R2_ENDPOINT`、`R2_BUCKET` 四项都非空时，才会把 R2 配置写入 Worker；`R2_MEDIA_BUCKET` 同样要求这四项齐备。所以即使**只用图片**，也要把 `R2_BUCKET` / `R2_PUBLIC_BASE` 填上，否则整组 R2 配置都不会生效。
</Warning>

音乐桶的判定逻辑（代码层面）：

```
音乐上传目标 = （R2_BUCKET 和 R2_PUBLIC_BASE 都非空）? 音乐桶 : 媒体桶
```

也就是说：只要音乐桶的两个变量有一个为空，音乐就会自动落到媒体桶。发现音乐传到了媒体桶，先检查 `R2_BUCKET` / `R2_PUBLIC_BASE` 是否漏填。

## 由工作流自动写入的运行时变量

下面这个**不是**你填的 GitHub Secret，但很容易和上面的表混淆：

| 运行时变量 | 谁写入 | 作用 | 没有时 |
|------------|--------|------|--------|
| `CF_API_TOKEN` | **工作流自动写入**（值取 `CLOUDFLARE_API_TOKEN`） | 文章增删改后调 Cache Purge 接口清边缘缓存 | 不做缓存清除，新内容可能延迟 1~5 分钟生效 |

另外两个 AI 开关**需要你手动设置**，工作流不写：

```bash
npx wrangler secret put BLOG_AI_ENABLED --name kejiland   # 0/false/off = 整体关闭 AI
npx wrangler secret put BLOG_AI_PUBLIC  --name kejiland   # 0/false/off = 禁止匿名生成摘要
```

## 配置步骤

1. 进入 GitHub 仓库 → **Settings**
2. **Secrets and variables** → **Actions** → **Secrets** 标签
3. **New repository secret** → 填入 Name 和 Value
4. 重复添加所有 Secret
5. **重新运行一次部署工作流**，让运行时 Secret 生效
