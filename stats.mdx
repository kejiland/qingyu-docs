阅读与点赞都落在 D1 的两张表：累计计数 `stats`，每日聚合 `stats_daily`。接口本身**公开**（无需认证），但写入侧带服务端去重与频控。

## 读取计数

```http
GET /api/posts/:id/stats
```

**响应：**

```json
{
  "ok": true,
  "postId": "article-slug",
  "stats": { "likes": 25, "views": 100 }
}
```

文章还没有任何计数时返回 `{ "likes": 0, "views": 0 }`。响应头为 `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` + `Cache-Tag: stats:<id>`。

## 写入计数

```http
POST /api/posts/:id/stats
```

**请求体：**

```json
{
  "action": "views"
}
```

| action | 说明 | 去重窗口 | 频控 |
|--------|------|----------|------|
| `views` | 阅读 +1 | 同一 IP 对同一文章 **1 小时**内只计一次 | 每 IP 每分钟 **30** 次 |
| `like` | 点赞 +1 | 同一 IP 对同一文章 **30 天**内只计一次 | 每 IP 每分钟 **10** 次 |

<Warning>
`action` 只接受 `views` 与 `like`（注意是 `views` 不是 `view`），其他值一律 `400`「action 只能是 views 或 like」。
</Warning>

**响应（正常累加）：**

```json
{
  "ok": true,
  "postId": "article-slug",
  "stats": { "likes": 25, "views": 100 }
}
```

**响应（命中去重，幂等不重复加）：**

```json
{
  "ok": true,
  "postId": "article-slug",
  "stats": { "likes": 25, "views": 100 },
  "duplicated": true
}
```

<Info>
- 计数自增用 D1 原子 upsert（`ON CONFLICT DO UPDATE SET likes = MIN(likes + 1, 9999999)`），并发点赞 / 浏览不会互相覆盖，单篇上限 9,999,999。
- 写入后**回读最终计数**再返回，响应里的数字总是库内真实值。
- 返回的 `stats` 字段顺序是 `likes` 在前、`views` 在后（JSON 对象本身无序，前端按字段名取值）。
- 点赞写入后会按 `stats:<id>` 标签清边缘缓存；浏览是高频请求，**不**触发 purge，靠 `s-maxage=60` 自然过期。
</Info>

**错误响应：**

| 状态码 | 场景 | error |
|--------|------|-------|
| `400` | `action` 不是 `views` / `like` | `action 只能是 views 或 like` |
| `429` | 命中每 IP 每分钟频控 | `操作太频繁，请稍后再试` |
| `405` | 非 GET / POST | `Method not allowed` |
| `500` | D1 未绑定 | `数据库未配置：请创建并绑定名为 DB 的 D1 数据库` |

## 趋势数据（管理后台）

```http
GET /api/stats/trend?days=30
Authorization: Bearer <token>
```

需会话 token。`days` 取值被夹在 **1 ~ 90**（非数字或缺失时按 30 处理），返回**连续**的每日数据点（没有记录的日期补 0），可直接喂给仪表盘折线图。

**响应：**

```json
{
  "ok": true,
  "trend": [
    { "date": "2025-01-01", "views": 150, "likes": 12 },
    { "date": "2025-01-02", "views": 200, "likes": 18 }
  ]
}
```

响应头为 `no-store`。

## 数据存储

### stats 表（累计计数）

| 字段 | 类型 | 说明 |
|------|------|------|
| `post_id` | `TEXT` | 文章 ID（主键） |
| `likes` | `INTEGER` | 累计点赞 |
| `views` | `INTEGER` | 累计阅读 |

### stats_daily 表（每日聚合）

| 字段 | 类型 | 说明 |
|------|------|------|
| `post_id` | `TEXT` | 文章 ID（联合主键之一） |
| `date` | `TEXT` | 日期 `YYYY-MM-DD`（UTC，联合主键之一） |
| `views` | `INTEGER` | 当日阅读数 |
| `likes` | `INTEGER` | 当日点赞数 |

每次点赞 / 浏览都会同步 upsert 一行 `stats_daily`（`ON CONFLICT(post_id, date) DO UPDATE`）。`/api/stats/trend` 就是对这张表按日期 `SUM` 聚合。

<Note>
删除文章会连带删除 `stats` 计数，并**尽力**清理 `stats_daily` 的历史行；后者失败不阻断删除（聚合表属历史趋势数据，表缺失也允许）。详见[文章 · 删除文章](/posts)。
</Note>

## KV 去重与频控键

去重标记与频控计数都存在 KV 绑定 `BLOG`（**不是** feed / sitemap / 文章缓存）：

| Key | 用途 | TTL |
|-----|------|-----|
| `rate:like:<ip>:<分钟窗口>` | 点赞频控（10 次/分钟） | 120 秒 |
| `rate:view:<ip>:<分钟窗口>` | 浏览频控（30 次/分钟） | 120 秒 |
| `liked:<ip>:<postId>` | 点赞去重（30 天） | 30 天 |
| `viewed:<ip>:<postId>` | 浏览去重（1 小时） | 1 小时 |

<Warning>
KV 未绑定（`env.BLOG` 缺失）时，上表的去重与频控会**静默失效**——服务端只在日志里打一条 warning。存储数据仍写入 D1，功能不报错，但防刷能力消失。
</Warning>

## 静态模式

`mode: 'static'` 下没有后端，阅读 / 点赞存在浏览器本地：

| 键 | 存储 | 用途 |
|----|------|------|
| `qingyu.stats.<postId>` | `localStorage` | 该文章的 `{views, likes}` 计数 |
| `qingyu.liked.<postId>` | `localStorage` | 本机是否已点赞（防重复） |
| `qingyu.viewed.<postId>` | `sessionStorage` | 本会话是否已计过阅读（防刷新重复 +1） |

全部仅限本机，清缓存即丢失。详见[配置说明](/configuration)。
